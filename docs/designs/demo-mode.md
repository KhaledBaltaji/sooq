## Context

Pre-launch, MENA prediction market. Users need a way to test the platform — trading mechanics, LMSR pricing, position behavior — without risking real money. The plan under review introduces a parallel "demo universe" with its own markets, its own LMSR AMM (deeper liquidity), its own positions/transactions, and a persistent $10K demo balance per user. Real money flows are untouched.

## Premise

Three framings of "why demo":
1. **Marketing/acquisition** — no-login preview for visitors (out of scope, needs different UX)
2. **Onboarding/education** — help signed-up users learn before their first real deposit
3. **Engagement/retention** — give users a sandbox to explore mechanics anytime

The plan as written is sized for #3 (parallel universe, persistent balance, full feature set). #2 is implicitly served by the same infrastructure. #1 is explicitly deferred.

## Vision

### 10x Check
The 10x version would combine: no-login preview (anonymous demo sessions), guided first-trade tutorial, demo-to-real graduation flow with matching deposit bonus, demo leaderboard with a real-money launch-day prize, viral portfolio share links with OG image cards. That's a growth engine, not a feature. **Explicitly not pursued.** Pre-launch context favors lean scope.

### Platonic Ideal
A new user lands on the site without signing up, sees a live-looking market, places a fake trade in one tap, sees the price move, wins or loses, and the product says "want to do this for real? one-tap signup." That experience is ~3 weeks of build. **Deferred — not pursued at this stage.**

## Implementation Approaches (considered)

**Approach A: Parallel `demo_*` tables** (SELECTED)
- Effort: L (human: ~1 week / CC: ~45 min). 2-3 migrations, 1 cron, ~10 frontend files, ~16 tests.
- Zero risk to live tables. Clean mental model. Survives audits.
- Trade-off: schema duplication. Every future markets/AMM feature must remember to mirror.

**Approach B: `is_demo` flag on live tables** (REJECTED)
- Every aggregation and revenue query in the codebase would need `WHERE is_demo = false`. Miss one → polluted stats. Not safe for fintech at pre-launch.

**Approach C: $10 seeded learning account** (DEFERRED as complement)
- Real-money onboarding via existing deposit-bonus plumbing. Cheap, proven infrastructure. Worth revisiting as a post-launch onboarding tool — not a demo replacement.

**Selected: Approach A** — real-money invariants are sacred. Schema duplication cost is minutes with CC. Isolation argument wins at pre-launch.

## Temporal Interrogation — Decisions Resolved

**Hour 1 — Foundations:**
- Migration 263 adds 5 columns to `users`. Postgres `ADD COLUMN ... DEFAULT ...` is table-lock-free on PG 11+. Safe.
- Migration ordering: 263 (tables + users columns) → 264 (RPCs) → 265 (seed catalog + AMM init)

**Hour 2-3 — Core logic:**
- RLS on `demo_*` tables: mirror live. `SELECT`: `user_id = auth.uid()` OR `is_admin`. `INSERT/UPDATE`: blocked from client (SECURITY DEFINER RPCs only).
- `demo_execute_trade`, `demo_reset_balance`, `toggle_demo_mode`: all derive user from `auth.uid()`, no client-supplied user_id.
- Realtime channel name must swap from `amm_state` → `demo_amm_state` when `demo_mode` toggles. Existing `UserProvider` re-subscribes on profile updates — confirm channel re-subscription in `markets-page-client`.

**Hour 4-5 — Integration:**
- **Audit every `supabase.from("markets" | "amm_state" | "positions" | "trades" | "transactions")` in the codebase.** Either route through a demo-aware wrapper helper (`getMarketsTable(demoMode)`) or add an inline `// eslint-disable-line demo-aware` comment. This is the single biggest quiet risk.
- Admin market creation: conditional render on same `/admin/markets/create` page (is_demo checkbox reveals scheduled_outcome + resolves_at fields). Don't duplicate the page.
- Conversion analytics wiring happens in `demo_execute_trade` (first trade timestamp) and `process_deposit` (first-real-after-demo timestamp). Both writes are idempotent (only write if null).

**Hour 6+ — Polish/tests:**
- Starter catalog content: user to write 15-20 bilingual market questions in migration. Claude can draft a bilingual markdown doc for review before insertion.
- Test fixtures: new helpers in `src/tests/db/helpers.ts` — `createTestDemoMarket(resolvesAt, scheduledOutcome)`, `enableDemoMode(userId)`, `fundDemo(userId, amount)`.
- 4 new test files: `demo-trading.test.ts`, `demo-resolution.test.ts`, `demo-reset.test.ts`, `demo-toggle.test.ts` (total ~16 test cases).

## Architecture Concern Flagged for Implementation

**Quiet-failure risk:** Every direct call to `supabase.from("markets")` or `from("amm_state")` / `from("positions")` / `from("trades")` / `from("transactions")` across the codebase will silently show the *live* universe regardless of demo mode unless it's explicitly demo-aware. Mitigation during implementation:

1. Grep all call sites: `grep -rn 'supabase.from("\(markets\|amm_state\|positions\|trades\|transactions\)"' src/`
2. Tag each as: (a) demo-aware (swap by mode), (b) intentionally live-only (add comment), (c) broken (fix)
3. Add an ESLint custom rule or a comment-based convention so future code stays conscious

## Commission Isolation (confirmed)

- Referral/agent tree lives on user record, never changes with demo mode.
- `demo_execute_trade` does NOT call `pay_trade_commissions` or `record_revenue`.
- `demo_resolve_market` does NOT call `settle_resolution_commissions`.
- Demo trades do not write to `commissions`, `platform_revenue`, `leader_stats`.
- Demo resolutions do not touch branch pool or branch settlement.
- Referral link behavior: unchanged. User B signing up through A's link is permanently linked regardless of whether B ever touches demo mode.

## Review Sections — Summary

The full review ran across 11 sections. Key findings:

- **Section 1 (Architecture):** 1 major concern flagged → demo-aware query audit (see above). Otherwise clean.
- **Section 2 (Errors):** `demo_execute_trade` must raise on: insufficient demo balance, closed/resolved demo market, market not found. Demo reset balance: only safe if demo_mode enabled. Cron: must handle "scheduled_outcome null" gracefully (skip + log). No catch-all exception swallowing.
- **Section 3 (Security):** Low surface-area expansion. Key rule: `auth.uid()` everywhere in demo RPCs, no `p_user_id` client-supplied. RLS on all `demo_*` tables matches live. Admin-only creation/resolution.
- **Section 4 (Data flow):** Demo trade must be atomic (SELECT FOR UPDATE on users + demo_amm_state + demo_positions). Toggle must be atomic (user enable writes balance row + timestamp in one transaction).
- **Section 5 (Code quality):** DRY concern — reuse `lmsr_cost`, `lmsr_price`, `lmsr_shares_for_cost`. Name new RPCs consistently with `demo_*` prefix.
- **Section 6 (Tests):** 4 test files planned, ~16 cases. Critical: test that demo activity writes 0 rows to live `transactions`, `commissions`, `platform_revenue`, `positions`, `amm_state`. Include a stress test that alternates demo+real trading on the same user.
- **Section 7 (Performance):** Deeper liquidity (b=5000) = smaller price moves per trade = more volume before price discovery noise. No N+1 risk — demo positions queried by user_id with index.
- **Section 8 (Observability):** Add `system_logs` entries for: demo enable, reset, trade, resolve, conversion. New admin dashboard tile surfaces conversion funnel.
- **Section 9 (Deployment):** Safe migration sequence. No feature flag needed (toggle is built in). Rollback: drop demo_* tables + revert users column adds. Zero live-data risk.
- **Section 10 (Long-term):** Reversibility 4/5 (one-way on data model, but no user-facing lock-in). Schema duplication is ongoing tax — budget 10-15% of future markets/AMM feature effort for demo mirroring.
- **Section 11 (Design):** Not evaluated deeply — surface-level coverage with visual language cherry-pick accepted. Recommend `/plan-design-review` for full UI audit before ship.
